# RAG governance: data rules, threat model, targets and decisions

Covers RAG plan tasks P0-01 (decisions), P0-02 (data classification), P0-03 (ID scheme), P0-04 (threat model) and P0-07 (targets). "Status" lines say what the code does today, not what is planned.

---

## 1. Data classification (P0-02)

| Class | Examples | May be embedded? | May be sent to the chat / embedding vendor? | May be logged? |
|---|---|---|---|---|
| **Public policy** | Loan policies, FAQ, requirements (`data/policies`) | Yes | Yes | Titles and counts only |
| **Application facts** | Amount, term, product, status, stated income, employer | No (served from the database) | Only the fields a status answer needs | No |
| **NPI / PII** | Full SSN, SSN last-4, date of birth, address, phone, email, account numbers, credit score | **Never** | **Never** (redact first) | **Never** |
| **Document content** | Pay stubs, licences, bank statements, extracted text | Not today. Later only after redaction (P3-03) | Not today. Vision extraction sends the image to the extraction provider | Never |
| **Internal review** | Exception rationale, waivers, review history, fraud-signal explanations | No | No | Action name only |

Rules:
1. Raw SSN and full account numbers are never embedded, never put in object keys or IDs, never put in a prompt, never logged.
2. Authorization is decided by the server before retrieval. The model is never an access-control layer.
3. Borrower answers must not reveal detection logic (audience tag `internal`, plan P5-05).
4. A new vendor that sees class "Document content" or above needs a vendor review first (P8-02).

Status: policy text is the only thing embedded. The question text goes to the embedding and chat vendors unredacted (decision D10), so the chat should not be used to type SSNs. The borrower API view already hides credit score, audit trail and exception rationale.

## 2. Tenancy and ID scheme (P0-03)

Hierarchy: **Bank (tenant) > Customer > Application > Document (versions) > Chunk.**

- IDs are opaque (MongoDB ObjectId today, UUIDv7 for new entities). No names, emails or SSNs in any ID or storage key.
- Object keys are generated by the server only: `t/{tenantId}/a/{applicationId}/d/{documentId}/v{n}.{ext}`; reusable KYC at `t/{tenantId}/c/{customerId}/kyc/{documentId}/v{n}.{ext}`. The original filename is metadata, never part of the path.
- Every query takes `tenantId` from the authenticated principal, never from a request body.
- Chunk IDs are deterministic: `hash(documentId, version, index)` so re-ingestion is idempotent.

Status: single bank, no tenant model (D01). Keys already use IDs only (`storage.js buildKey`), without the tenant prefix or version. Chunk IDs are already deterministic hashes.

## 3. Threat model (P0-04)

| # | Threat | Where it could happen | Control today | Gap / planned task |
|---|---|---|---|---|
| T1 | Another applicant's data reaches the wrong person | Chat route, retrieval | `chatAccess.js` scope check; unknown and forbidden IDs both return 404; named-applicant guard for borrowers | One `can()` module (P2-05); vector filters by tenant/application (P5-03) |
| T2 | Cross-tenant leakage | Retrieval, storage | Single tenant, so not yet reachable | Tenant model (P2-01); adapter refuses queries with no tenantId (P3-06) |
| T3 | Prompt injection through the question or history | Chat | Prompt treats question, history and evidence as untrusted data; model has no tools; citations must map to retrieved chunks | Injection test corpus (P7-04) |
| T4 | Prompt injection through an uploaded document | Future loan-file retrieval | Not reachable yet: document text is not embedded | Delimiters + output validation before P5-03 ships |
| T5 | Poisoned policy upload | Admin policy ingestion | Admin role only; text/PDF/MD only; 10 files x 10 MB | Review step and version history (P4-06) |
| T6 | Invented or altered numbers in an answer | Chat answer | Deterministic answers read amounts from the database; **new:** every number in a policy answer must appear in the cited evidence or the question (P5-04) | Tool-computed calculations (E17) |
| T7 | Invented citation | Chat answer | Citations accepted only if they map to a retrieved chunk; one retry, then a safe refusal | Citation-per-claim check (P6-05) |
| T8 | PII sent to a vendor or written to logs | Embedding/chat calls, logs | RAG logs record reasons and counts only; PII-bearing content is not embedded | Redaction before indexing (P3-03); log audit of other routes (P8-03) |
| T9 | Abuse or runaway cost (loop of questions) | `/chat` | **New:** per-user limit (20/min, `CHAT_RATE_LIMIT`); client disconnect cancels provider calls | Per-tenant token budgets (P6-08) |
| T10 | Provider outage hangs the assistant | Ollama / Chroma | Timeouts; **new:** circuit breaker on the chat model (3 failures, 30 s cooldown, fast "try again in a minute") | Failover to a second provider and a structured-only degraded answer (P6-06) |
| T11 | Stale or deleted document still retrievable | Future loan-file index | Not reachable yet | Supersede/delete sync (P3-08) |
| T12 | Exposed secrets (JWT, setup secret, API keys) | Config | Secrets only in env, `.env` ignored by git | Rotate exposed keys; secrets manager (P8-01) |

## 4. Targets (P0-07)

Measured with `npm run eval:retrieval` (retrieval) and the security tests (leaks). Starting values for a jury demo and a first pilot; tighten after the first measured run.

| Measure | Target | How measured |
|---|---|---|
| Retrieval recall@5 on the golden set | >= 0.90 (CI gate floor 0.80) | `data/eval/golden-policy-questions.json` |
| Retrieval MRR | >= 0.70 | same run |
| Citation validity (every cited source is a retrieved chunk) | 100% | enforced in `parseGroundedAnswer`, tested |
| Numbers in policy answers not found in evidence | 0 shown to users | enforced, tested |
| Cross-application or cross-tenant leaks in the security suite | 0 | `test/rag`, `test/chat` |
| Chat latency, p95 | <= 8 s (policy), <= 1 s (status, deterministic) | to measure once monitoring exists (P8-05) |
| Questions out of scope answered with a refusal | 100% of the golden out-of-scope set | to add to golden set v2 (P7-07) |

## 5. Decision records (P0-01)

Short form. Options and reasoning for each are in the **Decisions** sheet of `LoanLensAI_RAG_Implementation_Plan.xlsx`; this table records what the team actually chose.

| ID | Decision | Chosen | Consequence |
|---|---|---|---|
| D01 | Tenant model | Bank = tenant (target). Single tenant for the demo | Add `tenantId` everywhere before a second bank onboards |
| D02 | Where uploads live | Private object storage; Cloudflare R2 behind `STORAGE_PROVIDER`, MongoDB bytes as the default | Production target Azure Blob; migration script not needed for demo (re-seed) |
| D03 | Google Drive / OneDrive for borrower files | Not used for borrower documents | Team documents only |
| D04 | Key scheme | ID-based, server-generated | See section 2 |
| D05 | Duplicate customers | Flag for review, never auto-merge. Proxy today: SSN last-4 + DOB | Replace with keyed hash of the full SSN (HMAC) in production |
| D06 | Vector store | **Chroma Cloud**, behind `chromaService.js` | Not Atlas Vector Search as first proposed; swap point is the Chroma adapter |
| D07 | Embeddings | Chroma Cloud Qwen3-Embedding-0.6B on Render; Ollama `nomic-embed-text` locally | Vendor needs zero-retention terms (P8-02); model name is tagged for future re-index |
| D08 | Search | Dense with distance cutoff for now; hybrid + rerank later | Measure the gain with the eval script before building it |
| D09 | Chat model | Provider switch `anthropic \| groq \| ollama \| mock`; Ollama Cloud on Render because the org has no Claude API funding | Same grounded prompt for all providers |
| D10 | What is embedded | Policy text only | Question text is not redacted; do not paste SSNs into chat |
| D11 | Who sees what | Borrower API view hides internal fields; audience tags still to build | P5-05 |
| D12 | Ingestion | Inline for policies; async jobs for loan files later | P3-01 |
| D13 | Retention / deletion | Open: needs compliance input | Do not build soft delete or legal hold until compliance sets the schedule |
| D14 | Channels | Web now; WhatsApp later through the same `/chat` contract | P9-04 |
